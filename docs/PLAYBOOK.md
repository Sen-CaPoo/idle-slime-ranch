# 給 AI 遊戲創作者的實戰手冊

[English](PLAYBOOK.en.md) · [回到 README](../README.md)

這份手冊把《像素史萊姆牧場》的開發方法整理成**可以直接套用**的步驟。不論你用的是 Claude Code、其他 AI 編碼工具，還是一個人搭配一個 AI，都可以照著做。

---

## 1. 先定角色，再開工

一個 AI 什麼都做，很快就會在自己的盲點裡打轉。建議至少分成三個角色，每個角色一個獨立的工作階段：

| 角色 | 負責 | 不負責 |
|---|---|---|
| **引擎** | 狀態、數值、存檔、遊戲規則 | 畫面 |
| **畫面** | 繪製、動畫、介面、互動 | 數值 |
| **產品與驗收** | 好玩度、營利設計、平衡模擬、試玩、退回問題 | 自己寫的東西不自己驗收 |

人類扮演**導演**：給目標、做價值判斷（課金強度、授權、要不要公開），不必寫程式。

### 開場提示詞範例（給第三位加入的 AI）

```text
目前已經有另外兩個 session 正在開發一款 [類型] 遊戲。
你的任務是站在 [營利／視覺／好玩度] 的角度，讓這款遊戲
看得順眼、讓人想玩下去。先告訴另外兩位你的存在，讀完現有程式碼，
再提出具體建議。
```

## 2. 建一份共享記憶檔

在專案根目錄放一個所有 AI 都會讀寫的檔案（本專案是 [`COLLAB.html`](../COLLAB.html)）。最小模板：

```markdown
# 協作記憶

## 1. 任務
一句話描述目標。列出待確認的假設。

## 2. 檔案與分工
| 檔案 | 內容 | 負責 |

## 3. 介面合約 v1
// 引擎提供給畫面的全域 API
Game.state = { ... }
Game.actions.buy(id) -> bool
Game.on(evt, fn)  事件：'change'、'gold'、...

## 4. 進度紀錄
### 角色 A
- 日期：做了什麼、量到什麼數字
### 角色 B
...
```

規則：

- 每人只改自己的區塊。
- **改合約前先傳訊息取得同意**，再更新合約版本號。
- 每次做完一件事都記一行，附上數字。這份檔案就是之後交接、寫文件、回頭查問題的依據。

## 3. 用模擬取代感覺

這是本專案最有價值的一步。放置類、養成類、經營類遊戲特別適合，但任何有數值的遊戲都能用。

### 模擬器的最小結構

```js
// 1. 載入真正的遊戲邏輯（不要另寫一份簡化版）
for (const f of ['engine.js', 'shop.js']) vm.runInThisContext(read(f));

// 2. 假時鐘：讓 30 天在幾秒內跑完
let now = START; Date.now = () => now;

// 3. 玩家策略：每一步挑「每塊錢換到最多產量」的選項
function act() { /* 列出所有可買的東西，依 cost / gain 排序，買最好的 */ }

// 4. 情境：每天幾次上線、每次幾分鐘，中間用離線收益結算
for (const day of days) for (const session of plan) { offline(); play(session.minutes); }

// 5. 輸出：每場的「決策數」「最長空檔」「產量變化」與里程碑時間
```

### 要量什麼

| 指標 | 意義 | 本專案的標準 |
|---|---|---|
| 每場決策數 | 玩家上線時有沒有事做 | ≥ 5 |
| 最長空檔 | 會不會乾等 | < 90 秒 |
| 里程碑時間 | 第一次合成、第一次轉生、各地區解鎖 | 落在設計區間 |
| 長期目標 | 第 7、14、30 天還有沒有下一個目標 | 必須有 |
| 課金差距 | 輕課、重課比免費快多少 | 輕課 10–25% |

### 一定要做的事

- **多個隨機種子取中位數**，至少 5 個。單一種子可能剛好運氣好，會讓你誤以為平衡了。
- **模擬多種玩家**：免費、輕課、重課，以及「很少上線」與「一直開著」。
- **每次改數值都重跑**，並和上一版比較。

## 4. 驗收要可重現

每個驗收項目都要回答三個問題：**怎麼量？標準是多少？用什麼工具？**

### 畫面

- 用無頭瀏覽器（例如 Chrome 的 `--headless=new` 加 DevTools Protocol）自動開遊戲、點按鈕、截圖。
- 不要只截「靜態畫面」：揭曉、戰鬥、過場這類動畫要在不同時間點各截一張。
- 給出量化標準，例如「純白像素 < 5%」「角色輪廓可辨」。

### 效能

- 用 DevTools 的 CPU 降速（例如 4 倍）模擬手機。
- 量平均 FPS **和** p95 幀時間；只看平均會漏掉卡頓。
- 找一個最吃效能的情境（本專案是「神諭十連全部抽到最高稀有度」），用固定的亂數讓它可重現。

### 操作

- 用真實的滑鼠事件（`Input.dispatchMouseEvent`），不要直接呼叫函式，才能測到「長按」「被彈窗遮住」這類問題。
- 點擊前先確認目標沒被遮住；等待用輪詢，不要固定秒數。

## 5. 退回問題的寫法

好的退回訊息讓對方不用再問一次。格式：

```text
🔴 [嚴重度] 問題一句話
現象：在哪個畫面、做了什麼、看到什麼（附截圖路徑或數字）
標準：應該要怎樣（可量化）
建議：你覺得的修法（對方可以不採用）
```

實際例子：

```text
🔴 1. 機率公開表有錯（這是信用問題，最優先）：普通扭蛋的 SSR 欄列出
「極光、深淵、風暴」，但這三隻是神諭限定。我在 Node 用 3000 抽驗證過，
引擎確實不會抽到它們，所以是 UI 篩選只排除了 premium、沒有排除 oracle。
請修正，並檢查星輝扭蛋的表。
```

用 🔴（必修）／🟠（應修）／🟡（可以之後再修）分級，讓對方知道先做什麼。

## 6. 給 AI 的價值判斷規則

AI 很擅長「把要求做到最好」，所以如果要求是「讓人想消費」，它可能會走向誘導設計。把界線**寫下來**：

```markdown
## 課金原則
- 機率公開、有保底
- 付費取得的東西不會因為重置而消失
- 不使用：虛構原價、體力限制、差一點點的門檻、假倒數
```

本專案中，這些原則讓 AI 主動拒絕了自己同伴的錯誤建議（虛構原價），也主動發現了「差 10 元到 VIP5」這種不明顯的誘導。

如果要參考其他作品的風格，也要寫下智財原則：**只取類型風格，不複製具體設計**。

## 7. 一個版本的標準流程

```text
人類：給出目標
  ↓
產品：寫規格（含驗收標準與分工），寄給各負責人
  ↓
各負責人：平行實作，用防呆 API 互不阻塞，完成後回報數字
  ↓
產品：模擬 → 截圖 → 效能量測 → 操作驗收
  ↓
有問題 → 分級退回（附數字）→ 修正 → 再驗收
  ↓
全部通過 → 寫進共享記憶與版本紀錄 → 回報人類
```

## 8. 常見陷阱

| 陷阱 | 本專案的實際案例 | 預防方式 |
|---|---|---|
| 功能都做完，但不好玩 | v1.3 第 3 天起玩家就沒事做 | 第一版就寫模擬器 |
| 某個系統的數值破壞另一個系統 | 合成太划算，讓扭蛋失去價值 | 模擬時看「每種資源的取得時間點」 |
| 新內容擠壓舊內容 | 扭蛋角色占滿牧場格子 | 每次加內容都重跑 F2P 模擬 |
| 驗收腳本本身不穩定 | 固定等待 3 秒，冷啟動偶發失敗 | 輪詢等待、隨機 port、跑多次 |
| UI 顯示和實際規則不一致 | 公開機率表多列了角色 | 驗收時直接用引擎資料比對 UI |
| AI 無法驗證的面向 | 音樂好不好聽 | 輸出成檔案，明確列為「需要人類確認」 |
